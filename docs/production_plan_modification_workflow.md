# Production Plan Modification Workflow

## Purpose

This document describes how the Generate Item app propagates an approved Sales Order item or quantity change through BOMs, Production Plans, Work Orders, Material Requests, and Modification Tasks.

The main workflow is:

```text
Order Modification Request submitted
    |
    +-- Sales Order/item values are revised
    +-- BOM Modification Request is created for an item-code change
    +-- affected Production Plans are flagged
    +-- BOM Modification Task is created when a BMR is required
    |
BOM Modification Request submitted
    |
    +-- BOM components/revisions are updated
    +-- affected Production Plans are flagged
    +-- Production Plan Update task is created
    |
Production Plan > Update > Get Update
    |
    +-- original Production Plan data is captured once
    +-- planned quantity is refreshed from Sales Order Item
    +-- sub-assemblies are regenerated from the current BOM
    +-- raw-material planning rows are regenerated
    +-- linked Work Orders are flagged for update
    +-- Work Order/Purchase Order tasks are created
    |
    +-- Update > Create Material Request
    |       `-- creates an MR for remaining shortage quantities only
    |
    `-- Update > Update Work Orders
            `-- synchronizes every eligible linked Work Order from its BOM
```

## Entry point: Order Modification Request

`OrderModificationRequest.on_submit()` runs the modification workflow for the submitted request.

For an `Order Item Change`, it:

1. Updates Sales Order values and revision data.
2. Creates or updates batch information.
3. Calls `get_change()`.
4. Creates a consolidated BOM Modification Task when applicable.
5. Sets `sales_order_modification = "YES"` on affected draft or submitted Production Plans.

### Quantity change versus item-code change

- A quantity change updates the Sales Order Item quantity. The Production Plan is flagged through `sales_order_modification`, allowing its planned quantity and dependent rows to be refreshed.
- An item-code change is detected when an OMR row contains `rev_item` and the Sales Order still contains the old item. The implementation updates the Sales Order Item and related batch/BOM finished item, then creates or reuses a draft BOM Modification Request.
- A BMR is therefore specifically part of the item-change path. Quantity-only rows are skipped by `create_bom_task_on_omr_submit()` because they do not require the BOM-design task described there.

### BMR creation details

`get_change()` delegates to these helpers:

| Helper | Behavior |
| --- | --- |
| `get_mismatched_items()` | Finds OMR rows whose revised item differs from the current Sales Order Item. |
| `update_sales_order_items()` | Updates item code, name, description, batch, and BOM finished item data. |
| `create_order_modification_requests()` | Reuses a matching draft BMR or creates a new one, then copies current BOM components into it. |
| `update_child_rows_with_omr()` | Stores the BMR name in the OMR child row field `bom_update_request`. |

After these links exist, `create_bom_task_on_omr_submit()` creates one submitted `Modification Task` of category `BOM Modification` for the affected Sales Order.

## BOM Modification Request submission

`BomModificationRequest.on_submit()` performs the next gate:

1. `update_bom_items_using_db_set()` applies component changes to the linked BOM.
2. `update_bom_item_revision()` updates revision data and handles zero-value corrections.
3. `update_production_plan_bom_modification()` sets `bom_modification = "YES"` on every draft or submitted Production Plan whose `Production Plan Item.bom_no` matches the changed BOM.
4. `create_pp_task_on_bmr_submit()` creates a `Production Plan Update` task for each affected Production Plan.

The Production Plan client considers either `bom_modification` or `sales_order_modification` sufficient to show the **Get Update** action.

## Production Plan buttons

The three custom actions are grouped under **Update** by `production_plan.js`.

| Button | Current visibility rule | Server method |
| --- | --- | --- |
| Get Update | `bom_modification` or `sales_order_modification` has a value. | `generate_item.utils.production_plan.get_update_for_submitted_pp` |
| Update Work Orders | Production Plan is not cancelled (`docstatus != 2`). | `generate_item.utils.work_order.get_update_for_production_plan` |
| Create Material Request | Plan is submitted, `mr_items` is non-empty, `production_plan_updated == 1`, and the server reports at least one pending row. | `generate_item.utils.production_plan.create_material_request_for_pending_items` |

The button order is not a server-side workflow state machine. In particular, **Update Work Orders** is currently visible on every non-cancelled plan, even before **Get Update** has run.

## Get Update: Production Plan refresh

The client displays a confirmation and calls `get_update_for_submitted_pp(docname)` with a frozen form. The server then performs the following operations.

### 1. Execution-state validation

`validate_work_orders_before_update()` blocks the entire Production Plan refresh if any active linked Work Order has status:

- Started
- In Process
- Completed

Draft and Not Started Work Orders are allowed. Cancelled Work Orders are ignored.

### 2. Temporary handling of submitted plans

If the Production Plan is submitted, the method:

1. Closes the plan and updates bins.
2. Temporarily changes `docstatus` to draft.
3. Reloads the document and enables the flags needed to update a submitted document.

After regeneration and saving, it submits and reopens the plan. This is an implementation technique used to let standard ERPNext Production Plan methods rebuild child rows.

### 3. Capture the original plan once

`_capture_original_data_if_needed()` stores the pre-update state only when `original_data` is false:

| Live child table | Tracking child table |
| --- | --- |
| `po_items` | `tracking_assembly_items` |
| `sub_assembly_items` | `tracking_sub_assembly_items` |
| `mr_items` | `tracking_raw_materials` |

Before copying, `_validate_schema_match()` verifies that each tracking child DocType contains all non-system fields from its source DocType. A missing field stops the update with a schema error. After a successful copy, `original_data` is set to `1`, so later updates preserve the first baseline instead of overwriting it.

### 4. Refresh assembly quantity

`_sync_planned_qty_from_sales_orders()` fetches linked Sales Order Item quantities in one batch query. It changes `Production Plan Item.planned_qty` only when the Sales Order quantity is greater than the plan's current planned quantity.

Consequently, the current implementation handles quantity increases here but does not reduce `planned_qty` when the Sales Order quantity decreases.

### 5. Regenerate BOM-dependent rows

The method calls standard ERPNext behavior in this order:

1. `pp.get_sub_assembly_items()` rebuilds sub-assembly planning from the current `po_items` and BOMs.
2. `get_items_for_material_requests(pp.as_json(), warehouses=...)` recalculates raw-material planning rows.
3. `pp.mr_items` is cleared and repopulated with the calculated items.

If the Production Plan has a branch, `_get_default_transfer_warehouses()` selects the first enabled, non-group Warehouse for that branch with `store_warehouse = 1` and passes it as the source warehouse context.

The ERPNext material-request calculation is overridden in `hooks.py` by `generate_item.overrides.production_plan.get_items_for_material_requests_patched`, which is also part of the effective calculation path.

### 6. Set workflow flags

The refresh:

- sets `production_plan_updated = 1`;
- clears `bom_modification`;
- clears `sales_order_modification`;
- sets `modification_status = "Yes"` on every non-cancelled linked Work Order.

The cleared modification flags cause the Production Plan **Get Update** button to disappear after reload. The Work Order flag enables the individual Work Order **Get Update** button.

### 7. Create downstream Modification Tasks

For a previously submitted Production Plan, `create_wo_po_tasks_on_gate_update()` runs after the refreshed plan is resubmitted. It reads submitted OMR rows for affected items and creates:

- one `Work Order Update` task per affected linked Work Order;
- one `Purchase Order Modification` task per affected linked Purchase Order.

The task description contains the Sales Order, Production Plan, affected items, old/new quantities or item codes, and operator instructions.

## Create Material Request: shortage-only logic

The action does not blindly request the full recalculated raw-material quantity. It calculates the remaining quantity for each key:

```text
pending quantity = Production Plan required quantity - already requested quantity
```

The matching key is:

```text
(item_code, warehouse, sales_order)
```

### Already-requested quantity

`_get_already_requested_qty_map()` sums `Material Request Item.qty` from non-cancelled Material Requests where `production_plan` matches the current plan. It also includes legacy Material Request Items that have no Production Plan link but match a Sales Order used by current `mr_items`.

Cancelled Material Requests do not count. Blank and `None` key values are normalized before matching.

### Pending rows and button visibility

`get_pending_mr_items()` calls `_get_pending_mr_rows()` and returns:

- `pending_count`;
- display values such as `ITEM-001 (5.0)`.

The client adds **Create Material Request** only when `pending_count > 0`.

Example:

```text
Recalculated required quantity: 10
Existing non-cancelled MR quantity: 6
New Material Request quantity: 4
```

### Creation and concurrency protection

`create_material_request_for_pending_items()`:

1. Acquires a 60-second cache lock named `pp_mr_create_lock::<production-plan>`.
2. Reloads the plan and recalculates pending rows inside the lock.
3. Temporarily replaces the in-memory `mr_items` collection with only the pending rows.
4. Calls standard `ProductionPlan.make_material_request()`.
5. Restores the full in-memory collection.
6. Sets `production_plan_updated = 0` and commits.
7. Always removes the cache lock.

The lock limits duplicate Material Requests caused by a double-click or two near-simultaneous requests. When all quantities have already been requested, the method returns without creating another Material Request.

## Update Work Orders: bulk BOM synchronization

The Production Plan button calls `get_update_for_production_plan(docname)`. The method finds every non-cancelled Work Order linked through `Work Order.production_plan` and processes each independently.

### Per-Work-Order behavior

`_update_single_work_order()` rejects a Work Order when:

- it is cancelled;
- its status is Started, In Process, or Completed;
- it has no linked BOM.

For an eligible Work Order it:

1. Loads the current linked BOM.
2. Updates `production_item`, `item_name`, and `description` when the BOM finished item changed.
3. Rebuilds `required_items` using `get_bom_items_as_dict()` for the Work Order quantity.
4. Updates existing component quantities, rates, and amounts.
5. Adds BOM components not already present on the Work Order.
6. Removes obsolete components only when nothing has been transferred or consumed for them.
7. Keeps an obsolete component and warns the user when it has transferred or consumed quantity.
8. Saves the Work Order with update-after-submit enabled.
9. Sets `modification_status = "No"`.

New required-item rows inherit Work Order context including branch, Sales Order, batch, source warehouse, and BOM manufacturing flags.

### Partial-failure behavior

The bulk method creates a database savepoint for each Work Order. If one Work Order fails, only that Work Order is rolled back; processing continues for the others. Its response contains `total`, `succeeded`, `failed`, and a detail row for every Work Order.

The current Production Plan client does not inspect those counts and always shows a generic “Work Orders updated” success alert whenever the RPC returns a message. Developers changing this flow should display partial failures to the operator.

### Individual Work Order update

When a Work Order has `modification_status = "Yes"`, `work_order.js` displays its own primary **Get Update** button. It calls `get_update_for_work_order(docname)`, which uses the same `_update_single_work_order()` logic and then reloads the document. A successful update changes the flag to `"No"`, so the button disappears.

## State fields

| DocType | Field | Meaning in this workflow |
| --- | --- | --- |
| Production Plan | `sales_order_modification` | Set to `"YES"` after an OMR affects the plan's Sales Order. Enables Get Update. |
| Production Plan | `bom_modification` | Set to `"YES"` after a BMR affects a BOM used by the plan. Enables Get Update. |
| Production Plan | `production_plan_updated` | Set to `1` by Get Update; permits shortage MR action. Reset to `0` after an MR is created. |
| Production Plan | `original_data` | Indicates that the original child-table snapshot has been captured. |
| Production Plan | `tracking_assembly_items` | Original `po_items` snapshot. |
| Production Plan | `tracking_sub_assembly_items` | Original `sub_assembly_items` snapshot. |
| Production Plan | `tracking_raw_materials` | Original `mr_items` snapshot. |
| Work Order | `modification_status` | `"Yes"` means BOM synchronization is pending; `"No"` means the Work Order update completed. |

These are custom fields shipped through `generate_item/fixtures/custom_field.json`.

## Modification Task lifecycle and access

Tasks are inserted and immediately submitted with `status = "Pending"`. The task record contains category, subject, description, remarks, branch, and a Dynamic Link to the affected document. Submitted fields such as `task_status`, `task_remarks`, and `assign_to` remain editable.

### Task stages

| Trigger | Task category | Reference |
| --- | --- | --- |
| Item-changing OMR submitted | BOM Modification | Sales Order |
| Linked BMR submitted | Production Plan Update | Production Plan |
| Production Plan Get Update completes | Work Order Update | Work Order |
| Production Plan Get Update completes | Purchase Order Modification | Purchase Order |

### Role/category access

| Roles | Visible task categories |
| --- | --- |
| Design User, Design Manager | BOM Modification |
| Planning User, Planning Manager | Production Plan Update, Work Order Update |
| Purchase User, Purchase Manager, Purchase Master Manager | Purchase Order Modification |
| Sales User, Sales Manager, Sales Master Manager | Sales Order Modification |
| Administrator | All categories and branches |

Users without one of the mapped roles are denied access. When a user has Branch User Permission records, they can access only tasks whose `branch` is in that permitted set. No Branch User Permission means no branch restriction.

### Notifications

`ModificationTask.on_submit()` calls `send_modification_task_notification()`. It creates a `Notification Log` alert for enabled System Users who:

- have a role mapped to the new task category;
- pass the branch restriction;
- are not the task owner.

## Hooks and deployment

The relevant registrations in `generate_item/hooks.py` are:

- `doctype_js["Production Plan"] = "public/js/production_plan.js"`;
- `doctype_js["Work Order"] = "public/js/work_order.js"`;
- Production Plan `before_save` calls `generate_item.utils.production_plan.before_save`;
- Work Order `before_insert` and `on_trash` call Generate Item handlers;
- the standard Production Plan raw-material calculation is overridden by the app;
- Modification Task query and document permissions call `modification_task_permission.py`.

After changing client code, rebuild assets and clear cache using the normal bench deployment procedure. Do not edit `sites/assets/generate_item/js/*.js` directly because a later build can overwrite those files.

## Transaction and safety behavior

- Get Update commits explicitly after refreshing the plan, flagging Work Orders, and creating downstream tasks.
- The Production Plan refresh is all-or-nothing until its explicit commit; a validation exception prevents the refresh.
- Bulk Work Order update isolates each Work Order with a savepoint, allowing partial success.
- Material Request creation uses a cache lock and recalculates shortages inside the lock.
- Required Work Order components with transferred or consumed stock are preserved even when removed from the BOM.
- Original Production Plan tracking rows are captured only once.

## Known implementation considerations

The following behaviors are important when maintaining or extending the workflow:

1. **Update Work Orders sequencing is UI-only.** The button is not gated by `production_plan_updated` or Work Order modification flags.
2. **Quantity decreases are not copied to planned quantity.** `_sync_planned_qty_from_sales_orders()` only updates when the Sales Order quantity is greater.
3. **Get Update replaces all `mr_items`.** The active method clears and appends raw-material rows. A commented alternative `_merge_mr_items()` exists but is not used.
4. **Bulk update failures are hidden by the current client alert.** The server returns detail, but the UI does not present it.
5. **Task creation is not visibly deduplicated in the stage-specific functions.** Repeating a gate can create additional submitted tasks unless another validation layer prevents it.
6. **Get Update task lookup should be reviewed for Sales Order scoping.** `create_wo_po_tasks_on_gate_update()` obtains a Sales Order but queries OMR child rows primarily by item code and submitted status.
7. **Permission bypasses are intentional but sensitive.** Submitted Production Plan and Work Order updates use ignore flags/permissions and therefore depend on the whitelisted endpoint access model and business validation.

## Developer verification checklist

Use test data with a submitted Sales Order, BOM, Production Plan, at least one linked Work Order, and branch/store warehouse configuration.

### Quantity increase

1. Submit an OMR that increases quantity.
2. Confirm `sales_order_modification = "YES"` on the affected plan.
3. Click Get Update.
4. Confirm planned quantity increased, sub-assemblies and raw materials were recalculated, and original tracking rows were captured once.
5. Confirm linked Work Orders have `modification_status = "Yes"`.
6. Create an MR and verify it contains only the pending quantities.
7. Run the action again and verify no duplicate pending quantity is requested.

### Item and BOM change

1. Submit an item-changing OMR.
2. Confirm the linked draft BMR and BOM Modification Task exist.
3. Edit and submit the BMR.
4. Confirm the BOM is updated, the plan has `bom_modification = "YES"`, and a Production Plan Update task exists.
5. Click Production Plan Get Update.
6. Confirm BOM-based sub-assemblies/raw materials changed and downstream Work Order/Purchase Order tasks exist.

### Work Order update

1. Click Update Work Orders on the Production Plan.
2. Confirm eligible Work Orders use the latest BOM finished item and required components.
3. Confirm successful Work Orders have `modification_status = "No"`.
4. Repeat with one Started Work Order and verify that it fails independently while other Work Orders continue.
5. Test removal of a component with transferred quantity and confirm the row is preserved with a warning.

### Access and notification

1. Submit each task category and verify the correct functional roles receive bell notifications.
2. Verify users with Branch User Permissions see only matching tasks.
3. Verify a user without a mapped role cannot list or open Modification Tasks.
